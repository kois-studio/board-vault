# Translating the interface

Board Vault is written in English and translated into Spanish (`es`), French
(`fr`), German (`de`), and Italian (`it`) with Angular's build-time
`@angular/localize`. The decision and its reasons are in
[ADR-0024](adr/0024-interface-languages.md); game titles follow
[ADR-0025](adr/0025-game-editions.md). This page is the working guide: how to
mark text, how to translate it, and which words to use.

## How it works

- Templates and TypeScript keep the English text. `i18n` attributes and
  `$localize` mark what is translated.
- `npm run i18n:extract` collects every marked message into
  `frontend/src/locale/messages.xlf` (English, XLIFF 2.0) and adds new
  messages to `messages.es.xlf`, `messages.fr.xlf`, `messages.de.xlf`, and
  `messages.it.xlf`, keeping the translations they already have.
- `npm run build` compiles once and inlines each language into its own folder
  (`dist/frontend/browser/en/`, `…/es/`, …), served under `/en/…`, `/es/…`.
  There is no lookup at runtime. Changing language is a full page load.
- A message's ID is generated from its English text, its meaning, and its
  ICU structure. Changing the English makes it a new, untranslated message.
  That is intended: the old translation no longer says the same thing.
- Two checks keep a gap out of production. The `prebuild` step runs
  `node scripts/i18n-translations.mjs check`, which fails when any message has
  no translation in any language, and the build itself fails on a message
  missing from a file (`i18nMissingTranslation: error`). CI also fails when the
  extracted files are stale ("Check extracted messages are current").
  `check` runs only through `npm run build`; a bare `ng build` skips it.

Every pull request that adds or changes a user-facing string therefore adds
the translation in **all four languages** in the same pull request.

What is not translated: the Administration area (internal, stays English),
log and error `message` fields from the API, and game titles (ADR-0025).

## Workflow

From `frontend/`:

1. Mark the text (see below).
2. `npm run i18n:extract`. Commit the changes it makes in `src/locale/`.
3. `npm run i18n:missing` prints every untranslated message as JSON: the
   unit ID, the English source, the description and meaning, and which
   languages miss it. `npm run i18n:missing -- es` limits it to one language
   (`es`, `fr`, `de`, or `it`).
4. Write the translations in a JSON file outside the repository, one entry
   per unit ID:

   ```json
   {
     "4272436583644511364": { "es": "Ahora mismo", "fr": "À l’instant", "de": "Gerade eben", "it": "Proprio ora" }
   }
   ```

5. `npm run i18n:apply -- <file.json>` writes them into the four files. It
   refuses a translation whose placeholders differ from the source and an
   unknown unit ID (and exits with an error), and still writes the valid
   ones. Fix the reported entries and apply again. The text goes into the
   XML as it is: write `&` as `&amp;` and a literal `<` as `&lt;`, and use
   `<` only for the source's own placeholders. Avoid `$&` and `$1` in a
   translation; the script would read them as replacement patterns.
6. `npm run build` (runs `check`) and look at the page in the language:
   `npm run start:es` (also `start:fr`, `start:de`, `start:it`). The
   development server reads the translation files only when it starts:
   restart it after editing or applying translations.
7. Before committing, look for translations that went stale (see
   [Review stale translations](#review-stale-translations)).

You can also edit the `.xlf` files by hand or in a translation tool. A
translated unit has a `<target>` after its `<source>` and
`state="translated"` on its `<segment>`.

### Review stale translations

When the English changes, the message gets a new ID and loses its
translation, so `check` catches it. One case slips through: a sentence with
an ICU expression inside it (see [Plurals and selects](#plurals-and-selects))
is extracted as two units, and when only the ICU changes, the outer unit keeps
its ID and its old translation, marked `state="initial"`. `check` passes and
the old text ships. After applying your translations, run (from
`frontend/`, in PowerShell):

```powershell
Select-String -Path src/locale/messages.*.xlf -Pattern 'state="initial"'
```

or, in Git Bash, macOS, or Linux:

```bash
grep -n 'state="initial"' src/locale/messages.*.xlf
```

and retranslate every unit it lists (apply sets them back to `translated`).
It should list nothing.

### Merge conflicts in the translation files

Two branches that both add messages conflict in the same `.xlf` lines,
because the files are sorted. Do not merge them by hand: take either side,
run `npm run i18n:extract` so every message from both branches is present,
re-apply the translations your branch added (keep your JSON file until the
pull request is merged), and check with `npm run i18n:missing`.

## Marking text in templates

Put `i18n` on the element that holds the text. Its value is the description,
or `meaning|description`:

```html
<h2 i18n="Heading of the list of upcoming game nights on Home">Coming up</h2>
<button appButton type="button" i18n="game night|Starts the session">Start</button>
```

- **Description**: where the text appears and what it does, for someone who
  cannot see the screen ("Button on a notification", "Empty state of the
  wishlist"). Write one for every message that is not obvious on its own.
- **Meaning**: use it only when the same English means two things that a
  language might translate differently. "Start" as a game night versus
  "Start" as a step in onboarding: same text, different meaning, so two
  messages. Messages with the same text and meaning share one translation.
- Do not set custom IDs (`@@my-id`). Generated IDs are what make a changed
  sentence untranslated again.
- Markup and bindings inside the element stay in the message as
  placeholders, so a whole sentence with a link or bold name is one message:

  ```html
  <p i18n="Hint under the empty shelf">Add the games you own from <a routerLink="/collection/browse">Browse</a>.</p>
  ```

  The translator sees `Add the games you own from <pc …>Browse</pc>.` and can
  move the link. Never split a sentence into several marked pieces.
- Text with no element of its own goes in `<ng-container i18n="…">`.
- Interpolations are placeholders too: `Hello {{ name }}` reaches the
  translator as `Hello <ph … disp="{{ name }}"/>`. Give the expression a clear
  name, because the translator only sees the expression.

### Attributes

Mark an attribute with `i18n-<attribute>`:

```html
<img i18n-alt="Picture of the game on its page" alt="Box cover" [src]="cover" />
<input i18n-placeholder="Search field in Browse" placeholder="Search games" />
<button type="button" i18n-aria-label="Closes the menu on phones" aria-label="Close menu">…</button>
```

This works for `alt`, `title`, `placeholder`, and any `aria-*` attribute with
fixed text.

**An `aria-*` attribute that contains an interpolation does not work with
`i18n-aria-*`.** `aria-label="Delete {{ name }}"` with `i18n-aria-label` is
extracted and translated, but Angular 22 renders the button with no
`aria-label` at all, in every language (checked on 22.2.3; `alt` and `title`
with an interpolation are fine). Build that text in TypeScript and bind it as
an attribute:

```ts
protected readonly deleteLabel = computed(() => $localize`:Button on a group person:Delete ${this.person().name}:name:`)
```

```html
<button type="button" [attr.aria-label]="deleteLabel()">…</button>
```

## Marking text in TypeScript

Use `$localize` for toasts, labels built in code, page titles, and anything a
template receives as a string:

```ts
this.toast.success($localize`:Toast after saving a game night:Game night saved`)
this.toast.success($localize`:Toast after adding a game to the shelf:${game.title}:title: is on your shelf`)
```

- The text between the first two colons is the description
  (`:meaning|description:` for a meaning too). The description ends at the
  next colon and the first `|` separates the meaning, so a description
  contains neither. A message whose text itself starts with a colon is
  read as metadata and fails: start it differently.
- Name every placeholder with `:name:` right after it (`${game.title}:title:`).
  Without a name the translator sees `PH`, `PH_1`.
- `$localize` works anywhere, including module-level constants (the section
  names in `layout/app-sections.ts`, for example): each language's build
  inlines the translation.
- Unit tests and the English development server run in English, so specs
  keep asserting English text.
- Page titles and descriptions come from `getPageMetadata()` in
  `app.component.ts` and are marked there.

## Plurals and selects

### In templates: ICU expressions

```html
<span i18n="Number of games on a shelf">{count, plural, =0 {No games} one {One game} other {{{ count }} games}}</span>
<span i18n="Status chip of a game night">{status, select, live {Happening now} completed {Played} other {Planned}}</span>
```

- Write `{{ count }}` for the number, **not `#`**. Angular's ICU does not
  replace `#`; it is shown as a literal `#`.
- Always include `other`. Add the categories the English needs (`=0`, `one`);
  a translator adds the ones their language needs. Spanish, French, German,
  and Italian need only `one` and `other`: French counts 0 as `one`, and the
  `many` category that Spanish, French, and Italian have for round millions
  falls back to `other`.
- **Make the ICU the whole message**, with complete sentences in each
  branch:

  ```html
  <p i18n="When the shelf was last updated">{minutes, plural, one {Updated {{ minutes }} minute ago} other {Updated {{ minutes }} minutes ago}}</p>
  ```

  An ICU inside a sentence (`Updated {minutes, plural, …} ago`) becomes two
  units: the sentence, with the ICU as a placeholder, and the ICU on its own,
  with no description. It is harder to translate and can go stale silently
  (see [Review stale translations](#review-stale-translations)).
- A select whose `other` branch is a fallback should still read well.

### In TypeScript: branch on the plural rule

ICU syntax inside `$localize` is not interpreted at runtime: it shows the raw
`{…, plural, …}` text. Choose between complete messages instead:

```ts
import { intlLocale } from '../../core/i18n/format'

const plural = new Intl.PluralRules(intlLocale()).select(count)
const text =
    plural === 'one'
        ? $localize`:Games on a shelf, one:${count}:count: game`
        : $localize`:Games on a shelf, more than one:${count}:count: games`
```

Each language translates both messages. `one` covers what the page's language
counts as singular. If Russian or Arabic is ever added, this needs more
branches; until then `one` and `other` are enough.

The hand-built plurals in the code today (`n === 1 ? '' : 's'`, `countOf`,
the `count` pipe) build English words and cannot be translated: replace them
with an ICU in the template or the pattern above when you mark that text.

### Lists

Join names with `Intl.ListFormat`, never with `', '` and `' and '`:

```ts
new Intl.ListFormat(intlLocale(), { style: 'long', type: 'conjunction' }).format(names) // "Ana, Luis y Marta"
```

### Never build sentences by concatenation

`'Add ' + title + ' to your collection'` cannot be translated: word order,
articles, and agreement differ between languages. Mark the whole sentence
with a placeholder (`$localize`…`${title}:title:`…) or, in a template, one
`i18n` element with the binding inside it.

## Dates, numbers, and money

Never name a locale for display (`'en-GB'`, `'en-US'`) and never format with
`toLocaleString()` without one. Use the helpers in
`frontend/src/app/core/i18n/format.ts` or Angular's pipes; both follow the
page's language.

| Need | Use |
| --- | --- |
| A date or time | `formatDateTime(date, options, timeZone?)` |
| "Today", "In 5 days", "3 weeks ago" for a day | `relativeDays(days)` |
| "Just now", "5 minutes ago" | `timeAgo(date)` |
| A number | `formatNumber(value, options?)` |
| Money (collection worth, in euros, ADR-0016) | the `currency` pipe with `'EUR'`: `120 €` in Spanish, `€120` in English |
| The locale for another `Intl` API | `intlLocale()` (`en-GB`, `es-ES`, `fr-FR`, `de-DE`, `it-IT`) |
| A `YYYY-MM-DD` day key or `<input type="date">` value | `isoDay(date, timeZone?)`. It is a data format, never shown as text. |
| A phrase that starts a line | `capitalize(text)` |

English uses `en-GB` conventions on purpose: day before month, 24-hour clock,
week starting on Monday. Angular's `date` and `number` pipes use the build's
`LOCALE_ID`, which is plain `en` (United States conventions) in the English
build, so use the helpers; the `currency` pipe is fine for euros.

Pass `Intl.DateTimeFormat` options such as
`{ weekday: 'long', day: 'numeric', month: 'long' }`, not a fixed pattern
such as `'dd/MM/yyyy'`, so each language orders the parts itself.

## Game titles

A game title is not a message: it is the title of a published edition
([ADR-0025](adr/0025-game-editions.md)), *Codenames* in English and *Código
Secreto* in Spanish. Never mark a title for translation and never read
`titleTranslations.en` in a template or component. Show it with
`gameTitle(game)` or `{{ game | gameTitle }}`
(`core/utils/gameTitle.ts`): the title in the page's language when the
catalogue has it, else the English one. When the shown title is in another
language than the page, put `gameTitleLanguage(game)` in its `lang`
attribute. `otherGameTitles(game)` lists the other editions' titles, as the
game page does under its heading.

Sentences that name a game keep the title as a placeholder
(`$localize`…`${gameTitle(game)}:title:`…). When you mark a page that still
reads `titleTranslations.en`, switch it to `gameTitle` in the same pull
request.

## Languages and `OFFERED_LOCALES`

`frontend/src/app/core/i18n/locales.ts` holds two lists:

- `SUPPORTED_LOCALES`: every language that is built (`en`, `es`, `fr`, `de`,
  `it`). Each one is always reachable at its prefix, so a translator can check
  `/fr/…` before it is offered.
- `OFFERED_LOCALES`: the languages shown in the language menu and used to
  redirect an address without a prefix (the `bv_lang` cookie, then
  `Accept-Language`, then English). Today only `['en']`.

Add a language to `OFFERED_LOCALES` only when every message in it is
translated and, for French, German, and Italian, a native speaker has
reviewed it (ADR-0024). That is a one-line change and its own pull request.

### Adding a language

To add a language that is not in `SUPPORTED_LOCALES` yet (for example
Portuguese, `pt`):

1. `frontend/angular.json`: a locale under `projects.frontend.i18n.locales`
   (`translation` and `subPath`), a `pt` configuration under both `build` and
   `serve`, and `messages.pt.xlf` in the `extract-i18n` `targetFiles`.
2. `frontend/package.json`: a `start:pt` script like `start:es`.
3. `frontend/src/app/core/i18n/locales.ts`: `SUPPORTED_LOCALES`.
4. `frontend/src/app/core/i18n/format.ts`: the regional variant in
   `INTL_LOCALES` (`pt: 'pt-PT'`).
5. `frontend/scripts/i18n-translations.mjs`: `LOCALES`.
6. `frontend/src/locale/manifest.json`: the description for the web
   manifest.
7. `frontend/vercel.json`: the `:locale(en|es|fr|de|it)` patterns.
8. `frontend/middleware.ts`: the `(?:en|es|fr|de|it)` group in `matcher`.
   Without it, `/pt/…` counts as an address without a prefix and is
   redirected to `/en/pt/…`.
9. `backend/src/common/i18n/locale.ts`: `SUPPORTED_LOCALES`, so the API
   accepts its `Accept-Language`.
10. `npm run i18n:extract` creates `messages.pt.xlf`; translate every
    message, add a column to the [glossary](#glossary) below, and run the
    checks.
11. Update the language lists in [architecture.md](architecture.md#languages),
    [api.md](api.md), and ADR-0024.

Then offer it as described above.

## Tone and style

The English copy is plain, short, and speaks to the reader as "you". Keep
that in every language.

| | Spanish | French | German | Italian |
| --- | --- | --- | --- | --- |
| Variant | Spain (`es-ES`) | France | Germany | Italy |
| One person | tú ("¿Puedes venir?") | tu ("Tu peux venir ?") | du ("Kannst du kommen?") | tu ("Puoi venire?") |
| The group | vosotros ("Apunta a qué jugáis") | vous | ihr ("Was spielt ihr?") | voi |
| Buttons and menu items | infinitive ("Guardar") | infinitive ("Enregistrer") | infinitive ("Speichern") | imperative ("Salva") |
| Headings and labels | sentence case | sentence case | sentence case (nouns capitalised) | sentence case |

- **Sentence case** everywhere, as in English: only the first word and
  proper names start with a capital ("Mis juegos", not "Mis Juegos").
- German writes `du`, `dich`, `dein` in lower case.
- Never formal address (usted, vous for one person, Sie, Lei).

### Neutral wording, not gendered forms

Board Vault does not know anyone's gender, so nothing addresses or describes
a person in a masculine or feminine form. Rephrase instead of using slashes,
`@`, `x`, `·`, `*`, or `:` (no "invitado/a", "inscrit·e", "Spieler*innen").

| English | Spanish | French | German | Italian |
| --- | --- | --- | --- | --- |
| Welcome back | "Hola de nuevo" (not "Bienvenido") | "Content de te revoir" | "Willkommen zurück" | "Che bello rivederti" (not "Bentornato") |
| Players, attendees | "personas", "quienes vienen" (not "jugadores") | "personnes", "personnes présentes" | "Personen", "Anwesende", "wer kommt" | "persone", "chi viene" (not "giocatori") |
| Everyone | "todo el grupo", "cada persona" (not "todos") | "tout le groupe", "chaque personne" | "alle", "die ganze Gruppe" | "tutto il gruppo", "ogni persona" (not "tutti") |
| Invited (a person) | "con invitación" | "invitation envoyée" | "eingeladen" | "con invito" |
| Signed in as | "Has iniciado sesión como" | "Session ouverte : …" (not "Connecté") | "Angemeldet als" | "Accesso effettuato come" |

Words that agree with a thing, not a person, keep their grammatical gender:
"noche de juegos prevista", "soirée prévue", "serata conclusa".

### Typography

| | Spanish | French | German | Italian |
| --- | --- | --- | --- | --- |
| Quotes | «…» | « … » | „…“ | «…» |
| Questions and exclamations | ¿…? ¡…! | a no-break space before `? ! : ;` and inside `« »` | none | none |
| Apostrophe | ’ | ’ (l’étagère) | ’ | ’ (un’altra) |
| Numbers (from `formatNumber`) | 3,5 · 1234 · 12.345 | 3,5 · 1 234 | 3,5 · 1.234 | 3,5 · 1234 · 12.345 |

- Use the real characters: `’` (not `'`), `…` (not `...`), `–` for ranges
  ("2–4 personas").
- French spacing: type a no-break space (U+00A0) rather than a plain space
  before `? ! : ;` and inside `« »`, so the mark never wraps to the next
  line. In the JSON for `apply` write it as the escape `\u00a0`; it reaches
  the file as the character.
- Numbers, dates, and money come from the formatting helpers; never type a
  separator by hand.
- German and French text runs about 30% longer than English, and German
  compounds do not break. Check narrow buttons and chips at phone width.

French and Italian use "Annuler" and "Annulla" for both Cancel and Undo, as
their platforms do; Undo appears alone in a toast, so the two never meet.

### English inconsistencies to fix while marking

The source has a few variants for the same thing. When you mark one of these,
use the first wording and translate it with the glossary:

- "game night", "session", and "night" for the same thing (see above).
- "Hasn’t answered", "No answer", and "Waiting for your answer" for a missing
  answer: the first two describe someone else, the last one the reader.
- "Sign in" and "Log in": use "Sign in", as Clerk does.
- Straight and curly apostrophes (`can't`, `can’t`): use `’`. Changing the
  English changes the message ID, so do it in the pull request that marks
  the text.
