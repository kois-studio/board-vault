# API surface and contracts

## Current interface

The backend is an HTTP NestJS API with no global prefix. `main.ts` creates runtime Swagger at `/swagger` using `@nestjs/swagger`, installs a global strict `ValidationPipe` as a DTO safety net, and exposes bearer auth metadata and decorated DTOs. The API is consumed by the Angular client through the `Api` service and `DataService`; the production frontend environment targets `https://backend.board-vault.com`.

The runtime Swagger document is generated from source. There is no committed versioned OpenAPI artifact, generated client, consumer-driven contract, or contract-test gate. HTTP failures now use the safe `{ statusCode, code, message, details?, requestId }` envelope and include `X-Request-Id`; 5xx responses intentionally collapse provider and exception details to `Request failed`. The removed dashboard meeting-creation mutation has no remaining frontend client helper.

## Route families observed

| Area | Representative paths | Boundary notes |
|---|---|---|
| Auth | `/auth/status`, `/auth/register`, `/auth/login`, email verification, password reset | Public and authenticated paths are mixed; login, registration, password-reset, availability-query, and legacy token path inputs now use strict targeted validation and route-specific rate limits. Registration and availability checks return private-beta denial while self-registration is disabled; unknown Clerk identities cannot be provisioned locally. Forgot-password returns the same success behavior for known and unknown emails, and verification/reset tokens have persisted expiry and one-time-use enforcement; broader DTO validation remains unresolved. |
| Users/profile | `/users/*`, `/profile/users/:userId/*` | The deprecated global `GET /users/` listing is administrator-only and deprecated `POST /users/` account creation has been removed; user-scoped profile reads and the deprecated single-user lookup require ownership; `PUT /users/:userId` uses strict nested DTO validation and rejects privileged/unknown fields; `PUT /users/:userId/games` validates positive integer game-ID arrays and rejects unknown fields; `POST /profile/users/:userId/proposals` validates typed proposal fields and non-negative integer duration/player values; invitation acceptance requires the authenticated user to be the invitation recipient. Self-profile responses use the private user shape, while nested group/invitation/play identities use only `id`, `username`, `displayName`, and `avatar`. |
| Collection | `/collection/users/:userId/*` | Feature controller applies JWT/verified guards and `UserOwnershipGuard` to every current collection read and mutation route, including activity, owned games, wishlist, and reviews; ownership metadata writes validate purchase price/date/notes, review writes require an integer score from 0 through 10, and both reject unknown fields. The frontend now validates browse, game-detail, ownership, wishlist, review, and activity responses. |
| Dashboard/groups | `/dashboard/users/:userId/*`, `/groups/*`, `/memberships/*`, `/invitations/*` | Dashboard group routes check user ownership/membership; deprecated group listing is limited to owned/member groups, membership listing is limited to the authenticated account, and legacy user-data controllers require verified-user state in addition to JWT authentication. Legacy group creation derives the creator from JWT and validates its body, other legacy group routes check membership/ownership, pending group-invitation reads are owner-only, invitation creation validates its body and lifecycle actions check sender/recipient ownership, and legacy invitation list/detail reads are now limited to the authenticated recipient or sender. Deprecated membership creation requires a pending invitation. Group owners can also create a Clerk email invitation through `/groups/:groupId/clerk-invitations`; the server creates the provider invitation and embeds only validated group context, while the accepting verified identity is provisioned and joined after the group-owner check succeeds. Group-history reads return completed sessions only; scheduled sessions belong to the upcoming/session views. The acquisition board adds member-scoped interest through `/groups/:groupId/acquisition-board` and keeps it separate from personal wishlist data; the new routes require group membership. V1 group membership is invite-only with owner/member roles. |
| Notifications | `/notifications/*`, `/profile/users/:userId/notifications` | Profile reads require user ownership; deprecated notification list, ID reads, creation, read-state updates, and deletes now derive or enforce the authenticated account; notification write bodies use strict targeted validation. |
| Meets/play | `/meets/*`, `/meetAccountGames/*`, `/play/users/:userId/*`, `/play/recommendations`, `/play/recommendations/feedback`, `/play/recommendations/signals`, `/sessions`, `/sessions/:sessionId`, `/sessions/scheduled`, `/sessions/:sessionId/status`, `/sessions/:sessionId/attendees`, `/sessions/:sessionId/shortlist`, `/sessions/:sessionId/played-games`, `/sessions/:sessionId/rsvp`, `/sessions/:sessionId/attendance` | User history requires ownership; legacy meet lists/details are limited to group members; meet-account-game create/delete derives the account from JWT and requires meet-group membership. The obsolete dashboard meeting-creation route has been removed so new sessions use the canonical session API. `POST /play/recommendations` validates group membership and selected attendees, then returns games owned by at least one selected attendee with player-count/duration filters, deterministic scores, and explanation fields. `POST /play/recommendations/feedback` validates the same group/attendee ownership boundary before storing lightweight feedback. `GET /play/recommendations/signals` exposes the latest interested/not-for-us state per current group member and game, without exposing email or other private account fields. `GET /sessions/:sessionId` is now the canonical member-scoped session detail read; the frontend uses it while legacy `/meets/*` reads remain compatibility routes. `POST /sessions` is the canonical completed-session write, `POST /sessions/scheduled` creates a scheduled session for selected group attendees (retaining all-member behavior only when the compatibility field is omitted) and accepts optional validated `plannedGameIds`, and `PATCH /sessions/:sessionId/status` allows the organizer to move scheduled sessions to active/completed/cancelled or active sessions to completed/cancelled. Organizer-only `PATCH /sessions/:sessionId/attendees` and `PATCH /sessions/:sessionId/shortlist` replace the editable session plan atomically, validating group membership and available games. Organizer-only `PATCH /sessions/:sessionId/played-games` records actual games played, reconciles planned games to skipped, and accepts optional per-game participant IDs without implying organizer participation; detail and write responses expose the canonical participant mapping. Invited members can `PATCH /sessions/:sessionId/rsvp` while the session is scheduled or active; only the organizer can `PATCH /sessions/:sessionId/attendance` after activation, supplying the invited account IDs who actually attended. RSVP and attendance are separate fields. Writes validate ownership/membership and use transaction boundaries where multiple relations change. |
| Admin | `/admin/*` | Controller uses JWT, verified-user, and admin guards; administrator catalog and proposal-review bodies use strict targeted validation, and admin resource IDs use `ParseIntPipe`; proposal approval, rejection, and duplicate actions derive reviewer identity from the JWT. |
| Cache | `/cache/print`, `/cache/reset`, `/cache/delete/:key` | Operationally sensitive endpoints are retained for controlled maintenance only and require a valid authenticated administrator token. The reset route remains deprecated and should not be used during normal operations. |

The list is intentionally representative rather than a second route registry. The source controllers and Swagger output are authoritative for exact routes.

## Contract findings

- `ParseIntPipe` is used on selected route parameters and `main.ts` installs a global strict `ValidationPipe` for DTO boundaries. Controllers retain targeted pipes where their request contract needs explicit local coverage. The bootstrap also applies an explicit 100 KB JSON/URL-encoded body limit; client negative tests and the remaining legacy response contracts are still open.
- `frontend/src/app/api/api.schemas.ts` validates auth status/token, availability, private profile, catalog/owned/wishlist/browse/game-detail game responses, group/member/game/invitation responses (including invitation creation and the user invitation feed), dashboard stats, notifications, reviews, collection activity, group-history responses, admin tags/games/proposals, user proposals and proposal stats, persisted meets, completed history, attendee/played-game compatibility writes, and the translation-backed optional legacy game title, plus legacy auth messages, session creation/status, meet details, recommendations, recommendation feedback, and the success-envelope mutations at the client boundary. New endpoints and client negative tests remain open.
- Compatibility policy, deprecation policy, pagination limits, and retry/idempotency behavior are not documented as stable contracts. The error envelope is now stable at the transport boundary, but representative producer/consumer contract tests remain open.
- Pagination helpers exist (`limit.pipe.ts`, `offset.pipe.ts`) and some admin operations are paginated, but maximum bounds and expensive-query behavior are not consistently evidenced.
- Proposal review operations derive reviewer identity from the JWT; the frontend no longer sends reviewer query parameters.
- `POST /sessions` derives the creator from the authenticated request. Its request contract rejects unknown fields, requires at least one attendee and game, and prevents participants from being outside the selected attendees.
- `POST /sessions/scheduled` derives the creator from the authenticated request. Its optional `plannedGameIds` must refer to games available to at least one member of the selected group and are persisted as `MeetGame.gameStatus = 'planned'` in the same transaction as the session and pending attendees. A terminal lifecycle transition (`completed` or `cancelled`) marks remaining planned games as `skipped` in the same transaction; detail responses expose `playedGames`, `plannedGames`, and `skippedGames` separately.
- `POST /sessions/scheduled` accepts optional `attendeeIds`; when present they must be non-empty group members and are persisted as pending attendees. Omission retains the legacy all-current-members default.
- `PATCH /sessions/:sessionId/shortlist` is organizer-only and replaces planned games atomically while a session is scheduled or active; `PATCH /sessions/:sessionId/played-games` records the games actually played, accepts optional per-game participant IDs, preserves participant links for older group-level clients, and returns played/skipped IDs plus the canonical participant mapping; `PATCH /sessions/:sessionId/rsvp` is invitee-scoped, while `PATCH /sessions/:sessionId/attendance` is organizer-only and records the invited members who actually attended.
- `POST /play/recommendations` derives the actor from the authenticated request. Its `attendeeIds` must be non-empty group members; eligibility requires ownership by at least one selected attendee. The score is deterministic and uses ownership coverage, selected-attendee ratings, optional duration fit, and a bounded adjustment from the latest selected-attendee interested/not-for-us decisions. Explanations expose those feedback counts. Feedback is persisted, and `GET /play/recommendations/signals` exposes the latest group-member decision state without private account fields; richer preference/history scoring is deferred.
- Empty recommendation responses include a constraint-specific reason based on selected-attendee ownership, player-count fit, and optional duration fit.
- Nested user response fields are intentionally narrower than self-profile/admin fields; `UserPublicDto` is the documented public identity shape. Response validation and a complete DTO inventory remain open.
- Multiple controllers mark endpoints deprecated without a migration/versioning contract.

## Effective rules for API changes

- Add or update the machine-readable contract with any externally consumed route change.
- Validate path, query, body, and response boundaries; reject malformed, oversized, unexpected, or unauthorized input before application logic.
- Use a stable safe error envelope. Never expose stack traces, secrets, formatted SQL, or provider credentials.
- Define maximum collection sizes and query limits.
- Define duplicate/retry behavior for every mutation that can be repeated by the client or network.
- Add endpoint/contract tests for permitted and denied paths before marking a task complete.
